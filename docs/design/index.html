1. 概述

INFA 監控後台是基礎架構各監控系統（Cacti、Zabbix、PRTG、Graylog…）的統一入口。使用者登入後，依區域看到自己有權限的子項目，點擊即另開分頁進入該系統。管理員可以建立帳號、設定每個帳號能看到哪些子項目。

角色

  • 管理員 admin：看得到全部子項目；右上角有「權限設置」，可管理帳號與子項目。
  • 一般使用者 user：只看得到被勾選的子項目，沒有權限設置入口。

六個區域（固定）

TWIDC · JPIDC · PHIDC · PH Office · PH Studio · SL Office

TWIDC 12 項、JPIDC 4 項已確定；其餘四區子項目待需求方提供。

3. 操作流程

開通一個新同事

管理員登入→⚙ 權限設置→＋ 新增帳號→填帳號、密碼→勾選可看的子項目→儲存→把帳密交給同事

新增一個區域的子項目

⚙ 權限設置→子項目管理→選區域、填 Location / Name / 網址→新增→回帳號管理替需要的人勾選

同事忘記密碼

⚙ 權限設置→選該帳號→填「重設密碼」→儲存→同事舊的登入狀態全部失效

4. 權限規則

以下規則必須在後端強制執行，前端隱藏按鈕只是體驗，不能當作權限控管。

#規則
R1未登入只能呼叫 /api/login、/api/logout，其他 API 回 401。
R2GET /api/items：管理員回傳全部；一般使用者只回傳 user.items 內的項目。
R3/api/admin/* 僅管理員可呼叫，否則回 403。
R4系統至少保留一位管理員：把最後一位管理員改成一般使用者時回 400。
R5管理員不能刪除自己的帳號。
R6刪除子項目時，從所有帳號的 items 中移除該 ID。
R7設定授權時，不存在的子項目 ID 直接忽略，重複 ID 去重。
R8重設密碼（管理員重設或自己修改）後，該帳號其他 session 全部失效；自己修改時保留目前這個 session。
R9刪除帳號後，該帳號所有 session 立即失效。

5. 資料模型

參考實作用單一 JSON 檔（data/db.json）。正式開發可改用任何資料庫，結構建議如下。

users

id         string   主鍵
username   string   唯一，不分大小寫比對
password   string   雜湊值（scrypt / bcrypt / argon2）
role       enum     'admin' | 'user'
items      string[] 可檢視的子項目 ID
createdAt  datetime

items（子項目）

id         string   主鍵
section    enum     六個區域之一
location   string   可空白，例如 TW
name       string   必填，例如 Zabbix
url        string   可空白；http(s) 開頭
order      int      排序用，新增時遞增

若用關聯式資料庫，users.items 建議拆成關聯表 user_items(user_id, item_id)，刪除子項目時以外鍵 ON DELETE CASCADE 處理 R6。

sessions

參考實作存在記憶體，重啟後需重新登入。正式環境可改存 Redis 或資料庫。閒置 8 小時過期，每次請求會延長。

6. API

全部為 JSON。請求必須帶 Content-Type: application/json（否則回 415），錯誤一律回 {"error": "訊息"}，訊息直接顯示給使用者。

方法路徑權限請求回應
POST/api/login公開{username, password}{user} + Set-Cookie
POST/api/logout公開—{ok:true}
GET/api/me登入—{user, sections}
GET/api/items登入—{sections, items[]}（依 R2 過濾）
POST/api/me/password登入{currentPassword, newPassword}{ok:true}
GET/api/admin/users管理員—{users[]}（不含密碼）
POST/api/admin/users管理員{username, password, role, items[]}201 {user}；重複帳號 409
PUT/api/admin/users/:id管理員{role?, items?, password?}{user}
DELETE/api/admin/users/:id管理員—{ok:true}
POST/api/admin/items管理員{section, location, name, url}201 {item}
PUT/api/admin/items/:id管理員{section, location, name, url}{item}
DELETE/api/admin/items/:id管理員—{ok:true}

user 物件（回傳給前端）

{ "id": "3fd743fa1d92515e", "username": "demo", "role": "user",
  "items": ["5d966fbef12c7c65"], "createdAt": "2026-10-21T07:23:52.423Z" }

狀態碼

400 欄位錯誤或違反規則 · 401 未登入／帳密錯誤 · 403 權限不足 · 404 找不到 · 409 帳號重複 · 413 請求過大（>1MB）· 415 Content-Type 錯誤 · 429 登入次數過多

7. 欄位驗證

欄位規則錯誤訊息
帳號必填，≤ 64 字，僅英數字與 . _ @ -，不分大小寫唯一帳號僅可使用英數字及 . _ @ -／帳號已存在
密碼8–200 字元密碼至少需 8 個字元
角色admin 或 user，其他值視為 user—
區域必須是六個區域之一區域不存在

Name必填，≤ 100 字Name 不可空白

所有文字欄位前後空白會被去除。

8. 安全需求

  • 密碼只存雜湊（參考實作用 scrypt + 隨機 salt），比對使用 constant-time。帳號不存在時也要做一次雜湊，避免用回應時間猜帳號。
  • Session cookie：HttpOnly、SameSite=Strict，HTTPS 環境加 Secure。
  • 寫入類 API 要求 JSON Content-Type，加上 SameSite=Strict，用來防 CSRF。
  • 登入失敗限制：同一 IP 15 分鐘 10 次。
  • 回應標頭：Content-Security-Policy、X-Frame-Options: DENY、X-Content-Type-Options: nosniff、Referrer-Policy: no-referrer。
  • 前端一律用 textContent 輸出使用者資料，不用 innerHTML。
  • 首次啟動建立管理員帳號；密碼由環境變數 ADMIN_PASSWORD 提供，未提供則隨機產生並印在主控台。
  • 正式環境放在反向代理（Nginx）後面並啟用 HTTPS。
